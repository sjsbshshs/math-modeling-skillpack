# Math Modeling Pro

把本 skill 视为带阶段门和独立验收的工程流程，不是模型或获奖结果的保证。模板、决策矩阵和 playbook 只提供候选方案；题目机理、数据证据和验证结果优先。

## 工作模式

- 默认按 Stage 1--6 执行，每个 Stage 结束后给出产物和未决风险，再等待用户确认。
- 用户明确要求全自动时可连续执行，但内部质量门不能跳过；模型失败时必须回退，不得带着异常结果写论文。
- 比赛进行中且时间预算已激活时，默认采用全自动连续模式，仅在出现否决、阻塞或交付契约冲突时暂停等待用户。
- 用户只要求某一阶段时，仅执行该阶段及其必要前置检查。
- 不把竞赛之外的网络、账号或外部写操作视为默认授权。

## 竞赛时间预算与止损点

比赛有硬截止时间。质量要求必须能在赛程内完成，否则会被静默跳过而形同虚设：

- 参考节奏（以 72 小时国赛为例，美赛按 100 小时等比放大）：前 1/3 完成审题、数据审计和各问题模型框架；中 1/3 集中求解与验证；最后 1/3 锁定结果、全文写作、编译与提交验收。
- 止损规则：进入最后 1/3 赛程后，无论模型是否完善，锁定当前最好且可辩护的结果转入写作；继续迭代模型必须有明确的失败判据支撑，不允许无限期修补。
- 质量门分层：时间不足时按 `references/quality-gates.md` 的最小必做集执行；扩展集未完成不是否决理由，但论文必须如实披露已做与未做的检验范围。
- 摘要专项：正文冻结后单独留 3--4 小时重写摘要，按 `references/paper-guides/abstract-writing.md` 的常见错误表和 `references/paper-guides/self-review-framework.md` 的摘要六要素冷读检查。

## 创新机制（强制发散）

创新不是灵感而是流程项。以下四项由阶段门强制执行，细则见 `references/innovation-mechanisms.md`：

1. 发散建模门（Stage 2）：查矩阵前先自建 2--3 个本质不同的表述，矩阵降级为对比基准。
2. 特殊结构识别（Stage 2）：列出本题 2--3 处“不一般的地方”，至少一处被模型真正利用并写入贡献证据表。
3. 数据假设循环（数据类赛题）：审计后产出可检验假设清单，被证实的非显然假设进入模型并作为发现陈述。
4. 洞察盲区红队审（Stage 4）：回答“评审期待看到什么而论文没处理”，能补则补，不能补如实写为局限。

## 六阶段工作流

### Stage 1：题目与数据审计

1. 读取 PDF/DOCX 题目以及全部附件，记录实际成功/失败项。
2. 对每个表或文件检查尺寸、字段、类型、缺失、重复、异常、单位、主键/引用和合并单元格。
3. 根据 `references/problem-decomposition.md` 拆解子问题，列出输入、输出、约束、评价标准、数据流与数学本质。
4. 建立“交付契约”：题目要求的文件名、sheet、字段、精度、行序、图表、路径或其他输出格式；每条条目标注两侧落点——结果文件侧与论文表格/图侧，两侧分别验收（`references/paper-consistency.md`）。
5. 对会影响模型结论的字段做语义确认：记录单位来源、编码映射、公式/缓存值、隐藏内容和人工解释；无法确认的含义不得静默猜测。
6. 数据类赛题在完成审计和初步探索后，按 `references/innovation-mechanisms.md` 机制三产出可检验假设清单，供 Stage 3 检验并纳入建模。

输出题目拆解、数据审计和交付契约（数据类赛题附假设清单）。无法读取的附件必须显式列为阻塞项。

### Stage 2：证据与模型选择

1. 需要外部证据时按环境可用的互联网检索 skill 执行；优先原始论文、标准和官方页面。
2. 检索次数由证据充分性决定。通常 3--5 组高质量检索足够，但不是硬性上限；记录检索式、来源、结论和适用边界。
3. 发散建模门：查矩阵之前，对每个子问题先自建 2--3 个数学本质不同的表述并比较；同时列出本题 2--3 处特殊结构并确定至少一处的模型利用方式（`references/innovation-mechanisms.md` 机制一、二）。
4. 结合 `references/model-selection-matrix.md` 与相应 cookbook，为每个问题提出至少一个主模型和一个可解释的基线/替代模型；矩阵条目与自建方案冲突时书面说明取舍；简单问题无需人为凑多个复杂模型。
5. 明确选择理由、所需假设、可辨识参数、预期数量级和失败判据。
6. 核验文献真实存在并可追溯；不把搜索摘要本身当作论文证据。
7. 为每个主要模型建立“贡献证据表”：区分标准方法、题目适配和可能的创新；特殊结构利用与数据假设是贡献的主要候选来源；至少指定一个可复现的基线或消融比较，避免仅凭模型名称宣称创新。

输出发散比较、证据表、选定模型、基线和失败判据。

### Stage 3：实现、求解与模型否决门

1. 按题型读取相关 cookbook，并在 `references/playbooks/` 中选取匹配的题型 playbook（评价决策、ML 分类/回归、路径规划、物理 ODE、调度优化、策略博弈、数据洞察、几何运动学、MCM 政策/环境/网络）；模板仅作起点，必须改成题目变量、约束和数据接口。
2. 分离计算与展示：核心求解必须可在不绘图时运行；绘图只消费已生成结果。
3. 固定随机种子或记录随机状态、依赖版本、参数与运行入口；输出到用户要求的原始模板副本。
4. 执行主程序，不得凭空填写结果。
5. 在进入论文前执行 `references/quality-gates.md`：
   - 硬门（永远必做）：单位、边界、数量级与不变量；约束可行性和守恒闭合；基线/解析极限/小样例；输出格式一致性；
   - 扩展验证按时间执行：参数灵敏度和关键假设情景；独立实现、收敛性或交叉算法（适用时）；输入不确定性传播和结果稳健性（适用时）；重复运行；
   - 时间不足时至少完成最小必做集，扩展项未做须在论文中如实披露检验范围。
6. 任一硬门失败时回退模型或实现。程序“返回码为0”不等于模型通过。
7. 优化/调度问题必须记录可行性、停止原因、随机状态、最优性 gap 或“当前最好可行解”口径；没有证明时不得写成全局最优。

图表按论证需要生成：每张图必须回答一个问题。通常每个主要问题 2--6 张有效图足够，但不设最低数量；避免重复表达同一结论。默认使用项目现有绘图库；新建 Python 项目优先 matplotlib，除非用户或现有代码另有选择。

输出完整代码、结果、统计、验证报告、复现指纹和风险说明。

### Stage 4：论文写作

1. CUMCM 读取 `references/paper-guides/cumcm-guide.md`；MCM/ICM 读取 `references/paper-guides/mcm-icm-guide.md` 与 `references/mcm-specific-guide.md`。先确认当届官方规则，再使用本地模板。
2. 直接生成 LaTeX 源文件。论文只写已经由代码或证据支持的结果。
3. 论文数值单一来源：所有进论文的数字由结果文件或结果摘要经脚本生成，按语义键（时刻、对象 ID）取数，禁止手抄或把循环枚举序号当数据下标；取数后立即打印 2--3 个锚点与正文声称值比对（`references/paper-consistency.md`）。该纪律同样适用于非数值常量（决策位串、方案名等）：一律由脚本从结果文件生成并作为字符串声明登记，禁止手敲字面量。插图的所有标注/锚点值由绘图脚本从其绘制的同一数据列读取（禁止另取字段），登记到 `results/figure_manifest.json` 随一致性校验比对；重绘题目原图时，视觉评审必须附带题目原图对照。
4. 摘要包含方法、核心量化结果和检验结论，并在一页内；不机械套句式。
5. 公式数量由推导需要决定。定义、机理、目标、约束和求解关系必须完整，但禁止为满足数量堆公式。
6. 流程图仅在能显著澄清数据流、算法分支或子问题关系时使用，布局随问题设计，不套固定九框。
7. 短表使用普通三线表，跨页长表使用 `longtable`；按最长内容分配列宽并编译检查，不使用固定列宽公式。
8. 所有图表在正文解释并引用；所有参考文献真实、正文有引用、格式一致。
9. 附录与支撑材料清单覆盖所有生成论文结果所需的完整可运行源程序和必要数据。
10. 在摘要、引言或模型评价中明确列出 2--4 项本题贡献，并为每项绑定结果、基线、图表或代码证据；把“方法组合/题目适配”与“基础算法创新”分开表述。
11. 做一次反模板化审读：删除与题目无关的套话，检查“创新、最优、显著、精确”等强结论是否有对应证据。
12. 执行洞察盲区红队审（`references/innovation-mechanisms.md` 机制四；自审框架 1.4）：发现盲区能补则补证据，不能补的如实写为局限。

格式硬要求与写作增强项必须分开陈述。不要把字体、图数、公式数、流程图样式等本地偏好冒充官方规则。

### Stage 5：编译与视觉排版

1. 按 `references/cross-platform-execution.md` 发现 XeLaTeX、Python 和 PDF 工具；不要假设 Bash、固定盘符或系统代理。
2. 优先运行 `scripts/compile_paper.ps1`（Windows）或等价的本地编译命令；XeLaTeX 至少两遍。
3. 修复编译错误、未解析引用、字体回退、`Overfull`、`Underfull` 和过大浮动体。残留任何超容差的 `Overfull`（默认 >5pt，见 `scripts/check_official_compliance.py`）视为本阶段未通过——2024C 实战评审中一处 55.8pt 的溢行就是被外部评审点名的页边距硬伤。
4. 日志干净后仍必须做 PDF 检查：
   - 抽取每页文本，核对摘要、章节、参考文献、附录和连续页码；
   - 渲染页集按风险定向抽样：摘要页、正文首尾、每个插图页、重绘题目图页（附题目原图对照送审）、每个代码清单的首页与末页（跨页断行处确认无孤立碎片）、附录末页；机器校验覆盖不到的语义（曲线方向、图文一致）必须出现在视觉评审的检查单里。视觉评审的检查单至少包含以下基线（只可增不可减）：图表/公式/符号表在正文有显式引用，正文参考文献标注 [n] 可见，图表无遮挡与溢出，关键词分隔符全文一致，无孤行标题，页面无大片空白；
   - 检查裁切、吞字、重叠、空白图、乱码和字体嵌入；
   - 运行 `scripts/check_paper_consistency.py --paper <PDF> --summary <结果摘要>` 做论文↔结果数值/字符串比对（第三层）；
   - 运行 `scripts/check_official_compliance.py --paper <PDF> --tex <论文目录> --support <ZIP> --log <编译日志>` 做官方硬条款门：正文引用闭环、附录代码完整性、Overfull 残留、支撑清单↔压缩包一致、摘要首页。这些是格式规范的硬性条款，数值一致性工具覆盖不到、视觉评审看不出"缺了什么"，且历史上最容易在交付末端被跳过（2024C 实战：9 条文献正文零引用、附录代码覆盖 1%、支撑包 7 个文件未列入清单，全部是外部评审发现而内部各门放行的），所以做成机器门：任何 FAIL 必须修复后重跑，本项未跑视为此阶段未通过。
5. 不用手工 `\newpage` 掩盖浮动体问题；优先调整浮动体、屏障或条件式剩余空间。

输出最终 PDF、日志检查和视觉抽检记录。

### Stage 6：独立验收与提交

读取 `references/official-compliance.md`，并在比赛期间从官网复核当届版本。然后：

1. 从提交目录或压缩包在隔离临时目录运行，不使用工作区中未打包的隐式文件；运行前断言被导入的项目模块均位于隔离目录内（检查 `__file__`），防止工作区同名模块静默顶替隔离副本。项目源码不得含指向工作区的绝对路径（`scripts/audit_project.py` 的路径扫描默认报告为警告，须在复现说明中披露，`--strict-paths` 时按失败处理）。
2. 运行 `scripts/check_paper_consistency.py` 完成三层一致性比对（清单自洽、清单↔结果文件、清单↔PDF），并比对关键数值、结果文件结构和规范化指纹；Excel 需检查 sheet、表头、精度、公式/值和文档属性。
3. 核对 PDF 页面、文件大小、匿名性、引用、附录代码、支撑材料列表和压缩包 CRC。
4. 生成 MD5/SHA-256 后冻结最终文件；若再次保存，必须重新验收和计算哈希。
5. 最终结论只能是：通过、带明确除外项通过、或不通过。未检查的事项不能写成通过。
6. 记录规则来源 URL、访问日期、版本/修订日期和本地快照哈希；无法访问当届规则时将相关项标为未核验。
7. 在复现报告中记录解释器、依赖、TeX Live、操作系统、区域/编码和随机状态；路径、临时文件和工作区外依赖不得成为隐式前提。

交付前必须运行（任一 FAIL 未修复不得给出通过结论）：

```text
python <skill>/scripts/audit_project.py --project <项目目录> --paper <PDF> --support <ZIP>
python <skill>/scripts/check_paper_consistency.py --project <项目目录> --summary <求解/结果摘要.json> --paper <PDF> --strict
python <skill>/scripts/check_official_compliance.py --paper <PDF> --tex <论文目录> --support <ZIP> --log <编译日志>
```

前两个脚本检查数值与可观察事实；`check_official_compliance.py` 检查格式规范硬条款（引用闭环、附录代码完整性、Overfull、支撑清单↔压缩包一致、摘要首页）——这三类之外，比赛特定字段、模型物理真实性和官方当届规则仍需人工/项目级验证器。论文附录中的支撑材料清单表必须与最终压缩包逐项一致：打包晚于写作时，先改清单再压缩，不要靠目测。工作区中的过程文档（如求解计划.md）进入支撑包前须与最终实现核对一遍口径（参数、约束数值），过时草稿会让复核者怀疑实际执行的约束。

## 非协商质量原则

- 不伪造数据、文献、实验、精度或运行结果。
- 论文数值与结果文件单一来源；每个进论文的关键数字必须登记在结果摘要中并能经脚本从结果文件复现。
- 检验章每条“已验证”声明必须绑定可复核的运行证据（脚本、输出、报告时间戳）；无证据的一致性声明按未验证处理，不得写入论文。
- 模型假设必须写明影响范围；数值误差小不等于物理假设可靠。
- 预测使用样本外验证并防止数据泄漏；时间序列按时间切分。
- 优化报告可行性、约束残差、停止准则与基线；启发式不得无证据宣称全局最优。
- 机理模型检查单位、守恒、边界条件、稳定性和解析/极限情形。
- 评价模型说明指标方向、标准化、权重来源和排序稳定性。
- 任何“创新”结论都必须有与基线或消融的可观察差异；没有差异证据时只能称为标准方法的题目适配。
- 不确定性、结构假设和数据语义不确定性应与数值舍入误差分开报告。
- 官方规则优先于本 skill、模板和获奖论文惯例；规则冲突时记录并遵循官方当届版本。
